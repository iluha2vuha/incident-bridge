Engineering Handoff

This is a visual and interaction specification for a design prototype. It is not implementation code. Every mechanic below runs on local, simulated state only.

VISUAL DESIGN vs. SIMULATED BEHAVIOUR vs. FUTURE PRODUCTION
Everything rendered here is visual design. Navigation, vote selection, timers and vote counts are simulated prototype behaviour driven by local component state, not a server. Multi-device sync, real rooms, real votes, tie detection, persistence and reconnection are future production behaviour per PROTOCOL.md — none of it exists yet. Nothing here represents real multiplayer functionality.

1 · Screen inventory

Participant P01–P09 (P05 = round workspace, 10 role/round content variants). Facilitator F01–F13 (F05 = live round control, 7 variants; F07 = result/tie). Public/projector D01–D04 (optional, future scope). Full IDs listed on the Index tab.

2 · Flow maps

Participant: Join → Role → Lobby → Briefing → Round(×5) → Consequence → Transition → Debrief → Ended. Facilitator: Create → Lobby → Confirm → Briefing → Round control(×5) → Lock → Result/Tie → Reveal → Revealed → Debrief → End → Closed. Public: Join display → Round briefing → Result reveal (loops with facilitator) → Final debrief. Full diagrams on the Index tab.

3–4 · Component inventory, variants & interaction states

RoomCodeDisplay, QRPanel (placeholder), RoleCard, RoleBadge, ConnectionStatus, MetricCard, ChoiceCard (default/selected/disabled), ConfirmationSheet, VoteProgress, FacilitatorControlBar, TieResolutionPanel, ConsequencePanel, DecisionTimeline, EmailArtefact (mobile + desktop reference), TicketArtefact, AuthEventTable, MailboxRuleCard, ActiveSessionRow, RecoveryLogTable, EmptyState, ErrorState, ReconnectingBanner. Round-workspace interaction states (demonstrated fully on Round 1): no-choice, selected, confirm sheet, submitting, accepted, waiting, locked, disconnected, reconnecting. F05 states: prepared, open, votes arriving, all received, missing votes, disconnected, timer elapsed.

5–7 · Design tokens, type & spacing

See the Design System tab for live swatches. Ink oklch(0.15 0.01 260) for text/borders; Amber oklch(0.78 0.15 80) for active-incident state; HR coral oklch(0.62 0.14 35); IT blue oklch(0.55 0.12 255); green/red reserved for confirmed outcomes/genuine warnings. Type: IBM Plex Sans (UI/body, 16px+ on real devices), IBM Plex Mono (codes, IDs, timestamps only). Spacing scale 4/8/12/16/20/24/32px. Radius 0–4px.

8 · Responsive breakpoints

Participant: 360 / 390 / 430 CSS px, single column, no horizontal scroll. Facilitator: 1280 / 1440 CSS px. Projector: 1920×1080, 16:9, scaled preview only.

9 · Mobile layout rules

One primary action per screen. Minimum 44×44px touch targets. No layout depends on hover. Long artefacts scroll inside their own bordered region rather than the page. Sticky action area for Submit where the choice list is long.

10 · Facilitator desktop layout rules

Primary control (Open/Lock/Reveal/Next) stays in a stable position across round states. Vote-completion counts and missing-vote warnings sit above the fold. Private facilitator notes are visually separated (grey panel, "PRIVATE FACILITATOR NOTE" label) from anything shown on the projector preview.

11 · Projector layout rules

Large type (17px+ body, 24px+ headline scaled to 1920×1080). Never renders role-private information or individual votes — only shared updates, aggregate vote progress, and revealed results.

12–13 · Accessibility & motion

Role and status meaning is never colour-only — every role/status chip pairs colour with a text label. Focus-visible states, semantic buttons for all choices, error/status text linked contextually to its control. Motion limited to 150–250ms opacity/transform transitions (e.g. submitting → accepted); nothing essential relies on animation completing or on hover.

14 · Email artefact specification

Mobile: app bar (back + folder) → sender row with avatar, expandable From/To/Date → external-sender banner → subject → body → Reply/Reply all/Forward/More action bar. Desktop reference (Design System tab): rail → folder list → message list → reading pane → command toolbar. No Microsoft branding or login UI. Content sourced from the master brief's example (Maya Chen / Northstar Services), consistent with GAME_DESIGN.md Round 1 HR-private info. Email controls are inert — they never affect vote state.

15–18 · Other artefact specifications

BridgeDesk ticket: ID/status header, summary, field grid (priority/category/reporter/created), description. Authentication/MFA activity: timestamped row list (time, result, detail). Mailbox rule: row list (rule/destination/status). Active sessions: covered under the same row-list pattern as mailbox rules in Round 3 IT. Field-level detail beyond round 1's email/ticket and round 3's mailbox rule is a provisional operationalisation of GAME_DESIGN.md's narrative — flagged on the Index tab.

19–20 · Prototype-only vs. future-backend behaviour

Prototype-only: all navigation, all vote/interaction-state selection, all facilitator variant switching — driven by local component state, reset on reload. Requires a future backend per PROTOCOL.md: real rooms/room codes, authoritative round phase, server-side vote tallying and tie detection, reconnection via session tokens, role-filtered snapshots, and session cleanup.

21 · Content-source mapping

Shared updates, private info, all 4×10 choices, consequences, learning points and debrief questions are copied verbatim from GAME_DESIGN.md. Metric deltas shown in P06/F08/D03 are illustrative examples, not a live scoring engine. Role objectives on P04 are from PRODUCT_SPEC.md's Initial Roles section.

22 · Known limitations & open questions

Public/projector flow is optional per PROJECT_CONSTRAINTS.md. Anonymous export is intentionally omitted from F11 (not required for v1). Artefact field-level values beyond the brief's exact examples are provisional and open to content review. No accessibility contrast audit has been run against final rendered colours — recommended before build.
